# Architecture: API Access & Two-Factor Authentication

## Overview

Two independently-toggleable hardening features on top of the existing session-authenticated app, shipped together because #2 reduces the blast radius of #1:

1. **Personal access tokens (Sanctum)** — a user mints/lists/revokes their own scoped bearer token from `/user/settings`, for calling `/api/v1/*` outside the browser.
2. **Optional TOTP 2FA** (`laragear/two-factor`) — a per-user opt-in second factor on the existing `laravel/ui` session login.

Both surfaces are new sections on the existing Settings page (Vue islands), plus new `/api/v1/users/me/*` endpoints and (for 2FA) one new step inside the existing `/login` flow. No new page routes, no new top-level auth system — Sanctum was already the API guard for the whole `/api/v1/*` surface (26 controllers use `auth:sanctum`); this feature completes a partially-installed capability (`HasApiTokens` was on `User`, the migration/token issuance never was).

## Stack

- Laravel 12, `laravel/sanctum` (`personal_access_tokens` table — pre-existing in the squashed schema dump, not a new migration in this feature).
- `laragear/two-factor` (TOTP + recovery codes; own `two_factor_authentications` table, migration `2026_07_23_000001_create_two_factor_authentications_table.php`).
- `dedoc/scramble` for auto-generated OpenAPI docs at `/docs/api` (newly published `config/scramble.php`).
- Vue 3 Options API islands (`ApiTokenManager.vue`, `TwoFactorSettings.vue`) mounted on `/user/settings`; one new plain-Blade view (`resources/views/auth/two-factor-challenge.blade.php`) for the pre-auth login step.

## Auth Flow, End to End

**Session (SPA) requests** — unchanged. Cookie → `EnsureFrontendRequestsAreStateful` → guard resolves a `TransientToken`, whose `can()`/`tokenCan()` always returns `true`. No ability check applies.

**Bearer-token requests** — new. `Authorization: Bearer <token>` → Sanctum resolves the `PersonalAccessToken` row → `$user->currentAccessToken()` is that row, whose `can($ability)` checks the token's stored `abilities` array. Ability middleware (`abilities:read`/`write`/`settings`) is enforced on every `API` controller, matching `permissions.md`'s per-controller mapping — token management is the one exception, staying session-only regardless of abilities (see Trust Boundaries below). See `permissions.md` for the full mapping and `tests.md` for coverage (`tests/Feature/API/ApiAbilityEnforcementTest.php`).

**Login with 2FA** — `App\Http\Controllers\Auth\LoginController::attemptLogin()` delegates to `Laragear\TwoFactor\TwoFactorLoginHelper::attemptWhen()` (resolved from the container, not the facade, so it always holds the current request) instead of calling the guard directly. If the user has no confirmed 2FA, behavior is identical to `Auth::attempt()`. If confirmed, the helper flashes encrypted credentials into the session (`config('two-factor.login.key')` = `_2fa_login`) and re-renders the same `POST /login` response as the challenge view — there is no separate route or controller for the challenge step. `LoginController::validateLogin()` is phase-aware: if the flashed key is present, it requires only `2fa_code`; otherwise the normal credential fields. See `flows.md` for the full sequence.

## Trust Boundaries

| Boundary                                                               | Enforcement                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Browser → `/api/v1/users/me/tokens*`                                   | `auth:sanctum` + `verified` + an inline closure middleware in `ApiTokenApiController::middleware()` that `abort(403)`s if the resolved token is a `PersonalAccessToken` (i.e. a bearer-token caller). Only first-party session requests may manage tokens.                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| Browser → `/api/v1/users/me/two-factor*`                               | `auth:sanctum` + `verified` on all five actions; `enroll`/`confirm`/`disable`/`regenerateRecoveryCodes` additionally require Sanctum's `abilities:settings` middleware (`TwoFactorApiController::middleware()`) — the first real (non-session-only) use of the `abilities`/`ability` aliases registered in `bootstrap/app.php`. No-op for session requests (`TransientToken::can()` always `true`); a bearer token needs the `settings` ability to reach these. `show` (read-only) is ungated, matching every token's baseline `read` ability.                                                                                                                                                             |
| `POST /api/v1/users/me/two-factor/confirm` when 2FA is already enabled | Rejected with 422 before `confirmTwoFactorAuth()` is even called. **Hardened** — `laragear/two-factor`'s `confirmTwoFactorAuth()` short-circuits to `true` (skipping code validation entirely) once `hasTwoFactorEnabled()` is true, which previously let any caller past the ability gate retrieve the account's live recovery codes with an arbitrary/wrong code. The controller now checks `hasTwoFactorEnabled()` itself first and never delegates to that short-circuit path.                                                                                                                                                                                                                         |
| `POST /api/v1/users/me/two-factor/enroll` when 2FA is already enabled  | Rejected with 422 before `createTwoFactorAuth()` is called. **Hardened** — `createTwoFactorAuth()` unconditionally calls `flushAuth()`, which clears `enabled_at` and regenerates `shared_secret` even for an already-confirmed account, previously letting any caller past the ability gate silently disable and replace a victim's real 2FA secret with no password re-entry. Enrollment is now only reachable from a clean (not-yet-enabled) state; disable first (which is password-gated) to re-enroll.                                                                                                                                                                                               |
| Bearer token → any other `/api/v1/*` controller                        | `auth:sanctum` + `verified` + an `abilities:read`/`write`/`settings` gate per action, matching `permissions.md`'s mapping. A token is denied 403 on any action outside its recorded `abilities`, on top of the existing ownership checks (`$user->accounts()`, `$user->transactions()`, etc.). See `permissions.md` § "Full Ability Enforcement — Implementation Plan" for the complete per-controller mapping and `tests/Feature/API/ApiAbilityEnforcementTest.php` for coverage. |
| Disable 2FA / regenerate recovery codes                                | Requires re-entering the current password server-side (`TwoFactorPasswordRequest`, `current_password` rule) — not just a client-side confirm dialog.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| `SANDBOX_MODE=true`                                                    | All four mutating `TwoFactorApiController` actions (`enroll`, `confirm`, `disable`, `regenerateRecoveryCodes`) short-circuit to a 403 before touching the user record. `show` (read-only) is not gated. This did not exist in the original SPECIFICATION.md — see "Divergences from spec" below.                                                                                                                                                                                                                                                                                                                                                                                                           |
| Unauthenticated `POST /login`                                          | `throttle:6,1` on the whole login route (shared by both the credential step and the 2FA-code step, since they're the same route) — a 6-digit TOTP has only 1,000,000 possibilities, so this is load-bearing, not incidental. Layered under it, `LoginController::throttleKey()` gives the 2FA-code step its own per-account limiter (`ThrottlesLogins`' default 5/minute, no IP component for this step) so a distributed, multi-IP attacker can't dodge the guess budget by rotating source IPs — see `flows.md` step 4 "Hardening".                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| `/docs/api` in non-local environments                                  | `Gate::define('viewApiDocs', ...)` in `AppServiceProvider::bootEvent()`, driven by `config('yaffa.scramble_prod_auth')` (`none`/`user`/`guest`). `local` environment bypasses the gate entirely (Scramble's own `RestrictedDocsAccess` middleware).                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Per-user API rate limit                                                | `RateLimiter::for('api', ...)` in `AppServiceProvider::boot()` — `Limit::perMinute(120)->by($request->user()?->id ?: $request->ip())`, applied via `$middleware->api(append: ['throttle:api'])` in `bootstrap/app.php`. Replaces a prior production-only, IP-only, hardcoded `60:1` throttle. Applies identically to session and bearer-token requests.                                                                                                                                                                                                                                                                                                                                                    |

## Known Risks / Assumptions

- **Ability enforcement across the ~24 remaining controllers has shipped.** Every `API` controller now applies an `abilities:*` middleware gate matching `permissions.md`'s mapping, pinned by `tests/Feature/API/ApiAbilityEnforcementTest.php`. See `permissions.md` § "Full Ability Enforcement — Implementation Plan" for the mapping and rollout history.
- **No account-recovery UI path.** If a user loses both their authenticator device and all recovery codes, the only recourse is the operator running `php artisan app:user:disable-2fa {email}` on the server (`app/Console/Commands/DisableTwoFactorAuth.php`) — a deliberate break-glass design for a self-hosted, typically single-user app, not an oversight. The command logs a `Log::warning` with user id/email on use.
- **`SCRAMBLE_PROD_AUTH` default (`none`) matches pre-existing de facto behavior** (an undefined Gate resolves `false`), so this is a documentation/configurability improvement, not a behavior change on upgrade.

## Divergences from SPECIFICATION.md

- **Sandbox-mode gating on all four mutating 2FA endpoints** (`enroll`, `confirm`, `disable`, `regenerateRecoveryCodes`) is implemented but not mentioned anywhere in SPECIFICATION.md. Reasonable given the project has a public demo/sandbox mode (`config('yaffa.sandbox_mode')`, referenced elsewhere for a scheduled DB reset) where letting a demo visitor lock themselves out with 2FA would be a support problem — but it's undocumented intent, so noting it here for the spec to catch up.
- **`personal_access_tokens` migration file does not exist in `database/migrations/`** — the spec (§Migrations) says this explicitly: the table already existed via the squashed schema dump, so no migration was needed. Confirmed: `database/schema/mysql-schema.sql` already contains the table and its row in the `migrations` ledger. Not a gap, just worth the explicit note since a reviewer grepping for the migration file won't find one.
