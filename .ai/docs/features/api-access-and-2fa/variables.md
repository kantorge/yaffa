# Variables: API Access & Two-Factor Authentication

## New / Feature-Relevant Environment Variables

| Name | Used by | Scope | Source | Default | Rotation | Risk |
|---|---|---|---|---|---|---|
| `API_TOKEN_MAX_LIFETIME_DAYS` | `config('yaffa.api_token_max_lifetime_days')` → `ApiTokenRequest` (caps `expires_at`), `ApiTokenService::create()` (clamps when absent/too-far) | Server only | `.env` | `365` | N/A (not a secret) — lowering it does not retroactively shorten already-issued tokens | Low. Operational control, not sensitive. A misconfigured very-large value weakens the "no immortal token" guarantee the feature is designed to provide (no "never expires" UI option exists specifically to avoid this). |
| `SCRAMBLE_PROD_AUTH` | `config('yaffa.scramble_prod_auth')` → `Gate::define('viewApiDocs', ...)` in `AppServiceProvider::bootEvent()` | Server only | `.env` (commented out by default in `.env.example`) | `none` (matches pre-existing de facto behavior — an undefined Gate resolves `false`) | N/A | Low-medium. `guest` mode exposes route/schema shape (already public via the open-source repo, per SPECIFICATION.md's own risk analysis) and enables Scramble's "Try it" live-request UI at `/docs/api`, which can issue real requests using the visitor's own session credentials — not a privilege escalation, but worth knowing before flipping to `guest` on a non-demo production instance. |
| `OTP_TOTP_ISSUER` | `config('two-factor.issuer')` → shown in the authenticator app as the account label | Server only | `.env` | unset → package falls back to `config('app.name')` (verified in `laragear/two-factor` source: `getTwoFactorIssuer()` returns `config('two-factor.issuer') ?: config('app.name')`) | N/A | None — cosmetic only (which label the user's authenticator app shows). **Not present in `.env.example`**; the fallback makes this safe to leave undocumented, but a one-line mention alongside `API_TOKEN_MAX_LIFETIME_DAYS`/`SCRAMBLE_PROD_AUTH` would save an operator a vendor-source read if they want to customize it. |

## Pre-Existing Variables This Feature Now Also Reads

| Name | New usage in this feature |
|---|---|
| `SANDBOX_MODE` (`config('yaffa.sandbox_mode')`) | Gates all four mutating `TwoFactorApiController` actions (`enroll`, `confirm`, `disable`, `regenerateRecoveryCodes`) to a 403, both server-side and (for UX) client-side in `TwoFactorSettings.vue`. Not documented in SPECIFICATION.md — see `architecture.md` "Divergences." |
| `RUNS_SCHEDULER` (`config('yaffa.runs_scheduler')`) | The new `sanctum:prune-expired` daily job (`routes/console.php`) is added inside the existing `if (config('yaffa.runs_scheduler'))` block, so it follows the same main-container-vs-worker split as every other scheduled command — no new operational toggle needed. |

## No New Secrets Introduced

This feature does not add any new API keys, client secrets, or third-party credentials:

- Personal access token **plaintext values** are generated by Sanctum, returned once in the HTTP response, and stored only as a hash in `personal_access_tokens.token` — never logged, never re-displayed. Confirmed no controller/service in this feature logs the plaintext (`grep`-checked `ApiTokenApiController`, `ApiTokenService`).
- 2FA **secrets** and **recovery codes** are stored server-side (both `encrypted`/`encrypted:collection`, i.e. reversible via `APP_KEY` — not hashed — per `laragear/two-factor`'s own schema) and are never bundled client-side beyond the one-time enrollment/regeneration response.
- No new third-party API integration — `laragear/two-factor` is a local TOTP implementation (no outbound calls), and `dedoc/scramble` only reads existing route/validation metadata to build docs.

## Pre-Go-Live Checklist

- [x] **Full ability enforcement across the ~24 non-token, non-2FA `API` controllers** — see `permissions.md` § "Full Ability Enforcement — Implementation Plan". Shipped, pinned by `tests/Feature/API/ApiAbilityEnforcementTest.php`.
- [ ] Communicate to existing users (release notes / in-app notice) that already-issued tokens are now restricted to their recorded abilities — a token a script was unknowingly relying on for broader-than-selected access will start returning 403s on out-of-scope endpoints. No token re-issuance is required (the `abilities` column was already correct), but this is a real behavior change on upgrade, not silent.
- [ ] Confirm `API_TOKEN_MAX_LIFETIME_DAYS` is set to a value the team is comfortable with as the effective maximum unattended-credential lifetime (default 365 days).
- [ ] Decide `SCRAMBLE_PROD_AUTH` deliberately for each deployed environment — `none` (safe default) unless there's a specific reason to expose `/docs/api` outside `local`.
- [ ] Confirm `sanctum:prune-expired` is actually running (i.e. `RUNS_SCHEDULER=true` on whichever container owns the scheduler) — an expired-but-unpruned token still fails to authenticate (Sanctum checks `expires_at` on use), so this is a housekeeping/table-growth concern, not a security gap, but worth confirming operationally.
- [ ] Re-validate `laragear/two-factor`'s maintenance status and PHP 8.4/Laravel 12 compatibility before go-live, per SPECIFICATION.md's standing package-governance note — this was flagged as "not locked in" at design time.
- [ ] Verify the break-glass command (`php artisan app:user:disable-2fa {email}`) is documented for whoever holds server/DB access on the deployed instance, since it's the only recovery path for a user who loses both their authenticator and recovery codes.
