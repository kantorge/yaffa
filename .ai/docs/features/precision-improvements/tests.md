## Existing coverage

`MoneyCastTest` and `DecimalCastTest` (both `tests/Unit/Casts/`) are the direct, focused coverage for this feature's core mechanism: get/set/serialize round-tripping at the correct scale, currency resolution across all the branching cases the codebase actually has (parent-transaction relation, own-column relation, conditional account-vs-base-currency fallback), and the decimal-string wire format that is this feature's headline breaking change. `TransactionApiControllerConversionTest` pins the one piece of application logic this feature rewrote outright (`convertToBase()`), including the specific rounding-tie behavior a naive `amount * rate` float multiplication would have gotten wrong non-deterministically. `ScheduleInstanceTest` closes the loop on the one place `architecture.md` flagged as a manual, easy-to-miss re-implementation of the serialization contract outside Eloquent's own cast machinery.

This is solid, well-targeted unit coverage for a change that is entirely about type/serialization correctness rather than business logic or authorization (see `permissions.md`'s n/a note) — every cast, every currency-resolution branch, and the one non-Eloquent value object doing its own serialization all have a passing test today.

## Recommended CI gate

All coverage above is `tests/Unit/` — no DB fixtures beyond `RefreshDatabase`/factories, no external services. Already belongs in, and runs in, the standard suite:

```yaml
# .github/workflows/tests.yml (illustrative — adapt to the repo's actual CI file/runner)
- name: Run test suite
  run: vendor/bin/sail artisan test --compact
```

## Gaps — currently unverified

1. **`TransactionService::getInvestmentConfigCashFlow()`'s legacy currency-mismatch handling (`app/Services/TransactionService.php:189-205`) has no test.** This is the one place `architecture.md`'s "Known Risks" section calls out as deliberately not throwing: when an investment transaction's `price` (investment currency) and `commission`/`tax`/`dividend` (account currency) legs no longer share a currency — because the account or investment's currency was changed after the transaction was recorded — the method logs a `warning` (`"Investment transaction cash flow spans mismatched currencies (legacy data)"`, with the transaction id) and returns `null` instead of letting `Money::plus()`'s `MoneyMismatchException` escape. `tests/Unit/Services/TransactionServiceTest.php` has cash-flow tests for withdrawal/deposit/transfer/buy/sell/dividend, but none constructs a mismatched-currency investment transaction to exercise this branch. Proposed test: build an investment transaction whose `config` legs are `Money` instances in two different currencies (e.g. by changing the account's `currency_id` after the transaction detail row was created, bypassing `TransactionRequest::accountInvestmentCurrencyMatchRule()`'s create-time guard), call the cash-flow computation, and assert it returns `null` without throwing (optionally also asserting the warning is logged, via `Log::shouldReceive('warning')->once()`).
2. **The frontend `config.price` precision-truncation risk (`resources/js/shared/lib/helpers/index.js:198`, `processTransaction()`) is real, documented as still-open in `frontend-precision-followup.md`, and has no test on either side.** `architecture.md`'s Known Risks section confirms by code inspection that a `DECIMAL(20,10)` investment price fetched from the API can silently lose precision when converted to a JS `Number` and re-saved without the user touching the price field. This is a JS-side numeric-precision bug, not a PHP unit-testable rule — no backend test can pin it, and no frontend test currently does either. Flagged here rather than silently dropped since it's this feature's one confirmed still-open correctness gap; the fix (and its test) belongs with whoever picks up the follow-up doc, likely a JS test asserting a round-trip through `processTransaction()`/its inverse preserves all 10 fractional digits of a representative high-precision price.
3. **No test exercises `MoneyCast`/`DecimalCast::set()`'s over-precise-input tolerance directly at the cast layer itself.** `specification.md` FR-8 (Phase 5, ✅ Completed) closed the user-facing side of this gap with a `TransactionRequest`/`InvestmentPriceRequest` `decimal:0,<scale>` validation rule (see the table above) — deliberately at the request layer, not by tightening the cast, since a request-layer rejection is what a user actually sees and the cast stays a backstop for write paths that bypass the Form Request (e.g. `artisan tinker`, a queued job constructing a model directly). That backstop itself remains untested: `MoneyCastTest::test_set_accepts_a_plain_scalar_and_stores_it_at_the_exact_scale` only exercises a value already at-scale (`12.3` → a scale-4 column). Proposed test: write a value with more fractional digits than the column supports (e.g. `12.34567` into a scale-4 `amount` field) directly via the cast (bypassing validation) and assert it's silently rounded to `12.3457`, not rejected — pins the intentionally-permissive cast-layer fallback now that the request layer is the primary gate.
4. **`format.js`'s floor/ceiling `minimumFractionDigits`/`maximumFractionDigits` split (FR-8) has no automated test.** This repository has no JS test runner configured (no Jest/Vitest, no `*.test.js`, no `test` script in `package.json`); adding one to cover a single function is a new-dependency decision outside FR-8's own scope, not something introduced silently as a side effect. Verified manually instead (inspection of the rewritten function against representative cases) and via a successful production build. Proposed test, if/when a JS test runner is introduced: `toFormattedCurrency()` with a whole-number amount and `generic_decimal_precision: 2` still renders two decimals (floor not dropped); a value carrying real fractional content beyond the currency's configured precision, up to the field's storage scale, renders all of it (ceiling not truncated); a value at exactly the storage scale never renders past it even if `maximumFractionDigits` were mis-set higher.
