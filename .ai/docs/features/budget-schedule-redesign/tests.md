## Gaps — currently unverified

1. **`catchUpToDate()`'s 10,000-iteration cap (`MAX_CATCH_UP_ITERATIONS`) is undemonstrated by any test.** Every existing catch-up test uses a schedule that resolves in well under 10,000 iterations, so the cap-hit path (`RuntimeException` at the controller layer, `false` return with no partial `save()` at the model layer) has never actually executed under test. The recurrence-cost validation floor (see the coverage row above) makes this cap unreachable via normal request input in practice, but the cap itself — and its no-partial-state guarantee — is still worth pinning directly. Proposed test: `catchUpToDate()` with a rule engineered (independent of the request-layer floor) to resolve just past 10,000 occurrences; assert `false` is returned and `save()` is never called.
2. **`Budget::currency()`'s reuse of a pre-computed `$baseCurrency` for account-agnostic rows (`TransactionApiController::getScheduledItems()`, `ReportApiController::budgetChart()` — see `architecture.md`) has no differential query-count regression test.** Nothing currently fails if a future edit reverts to calling `$budget->currency()` unconditionally per row. Proposed test (both controllers): create several account-agnostic `Budget` rows, `DB::enableQueryLog()` around the call, assert query count stays flat as row count grows — same technique as `TransactionScheduleInstancesTest.php`'s N+1 regression test.
3. **`CalculateBudgetActiveFlag::handle()` has no dedicated unit test in isolation.** Its only coverage is the second (integration, end-to-end) test in `CalculateTransactionScheduleActiveFlagsCommandTest`, which proves the externally-observable outcome but not, e.g., that `saveQuietly()` doesn't re-fire the `updating` hook or dispatch `CalculateAccountMonthlySummary` (per `architecture.md`'s note that this job is intentionally different from the synchronous create/update path). Low priority.
4. **`CalculateTransactionScheduleActiveFlags`'s `lazy()` paging is untested at a page boundary** (Eloquent's default page size is 1000 rows). Every existing test seeds a handful of rows, well inside one page. Proposed test: seed more rows than one page (or override the page size for the test) and assert the dispatched-job count still matches the row count exactly across the boundary. Considered low priority and expensive to seed for — `lazy()`'s own paging is a well-tested Laravel primitive, not something this codebase needs to re-verify; this gap covers only the possibility of a hand-written bug at the boundary.
5. **`ReportApiController::budgetChart()` has no date-range bound and no caching, unlike its sibling `getCategoryWaterfallData()`.** `getCategoryWaterfallData()` takes an explicit `(year, month)` route param, resolves a bounded range via `resolveDateRangeForYearMonth()`, and wraps the whole payload in `Cache::remember()` keyed by `CategoryWaterfallCacheService::key()` (7-day TTL). `budgetChart()` (`ReportApiController.php:51` onward) takes no year/month/date-range parameter at all — it pulls every matching `TransactionItem` for the requested categories/accounts with no `whereBetween('date', ...)` and no cache layer, so a long-lived account accumulates an ever-growing, uncached full-table scan on every chart load. Checked `tests/Feature/API/ReportApiBudgetChartTest.php` (the coverage row above) — every case seeds a handful of months and asserts on chart *content*, none assert a request is rejected/clamped past some max span, and none assert a second identical request avoids re-querying (the way `ReportApiWaterfallTest::test_waterfall_response_is_cached_until_explicitly_invalidated()` does for the waterfall endpoint). No test currently pins either behavior. Proposed tests: (a) seed a very large number of months of transactions and assert `budgetChart()` either rejects/clamps the request or completes within a bounded query count — whichever the team decides is the intended fix; (b) once caching is added, mirror `ReportApiWaterfallTest`'s cache-hit/cache-invalidation pattern for this endpoint.
6. **`CategoryWaterfallCacheService`'s cache is invalidated on transaction create/update/delete (via `ProcessTransaction{Created,Updated,Deleted}`) but not on category rename/reparent/delete** — a stale category name or top-level grouping can be served from cache for up to the full 7-day TTL after an edit. Confirmed by inspection: no `CategoryObserver` or category-mutation listener exists anywhere in `app/Listeners/` or `app/Providers/` that calls `CategoryWaterfallCacheService::forgetForDate()`/`Cache::forget()` — the service's only call sites are the three transaction listeners. `tests/Feature/API/ReportApiWaterfallTest.php` (the waterfall cache-coverage row above) only exercises the transaction-mutation invalidation path; nothing renames, reparents, or deletes a category and re-asserts the cached waterfall payload. No natural existing home for this gap (`reports/` has no `tests.md` of its own; recorded here since the waterfall lives immediately adjacent to this doc's budget-chart coverage). Proposed test: populate and warm the waterfall cache for a category, rename (or reparent, or delete) that category directly via its API/service, re-request the same waterfall endpoint, and assert the response reflects the new name/grouping rather than the stale cached one — this will fail today and would need a category-mutation listener calling `CategoryWaterfallCacheService::forgetForDate()` (or a broader per-user cache flush, since a rename has no single transaction date to key off) as the actual fix.
7. **No frontend verification at all for the three hand-synced RRULE builders** (`HasRecurrenceRule::effectiveRrule()`, `processScheduledTransaction()`, `TransactionSchedule.vue` preview) or for `Schedule.vue`'s pattern descriptions. The repo has no JS test runner and CI runs no ESLint; no Dusk test references either new field. Manual checklist until a runner exists: for each of the three patterns × MONTHLY/YEARLY, confirm the form preview, the schedule display, and the Schedules & Budgets table agree with the backend's next occurrences.
