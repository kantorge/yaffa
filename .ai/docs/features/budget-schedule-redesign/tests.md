## Existing coverage

The core CRUD/authz surface of `Budget` is well covered: happy-path create/edit/delete (both account-agnostic and account-scoped), the two real ownership gates (`BudgetRequest`'s `category_id`/`account_id` checks, `BudgetPolicy::isOwnItem()` for existing-row access), the deliberate 403-not-404 existence-confirming shape, `active`'s full non-client-settability, and index-level user isolation. `BudgetMigrationTest.php` is thorough for the one-time data migration — all 4 documented risk-case guards plus the happy-path conversion (including the category-summing and hybrid-row edge cases) are pinned end-to-end against real schema rollback/re-migrate.

`ReportApiBudgetChartTest.php` is the standout: it directly pins the two subtlest FR-2 rules from `architecture.md`/`background.md` — that a multi-category schedule is summed once per period (not once per contributing category) and that account-scoped + account-agnostic `Budget` rows for the same category are *intentionally* summed rather than deduplicated, with the breakdown array asserted to expose both rows individually.

The recurrence/inflation math extracted into `RecurrenceRuleService` and `InflationCalculator` is unit-tested in isolation from any HTTP or Eloquent concern, including the specific boundary behaviors called out in `architecture.md` (calendar-year-boundary compounding vs. anniversary compounding, `by_day`/`by_month` ordinal-weekday resolution, inclusive vs. exclusive after-date, Recurr's default `virtualLimit` of 732 not silently truncating a 3-year-old DAILY schedule). `TransactionScheduleInstancesTest.php` specifically regression-tests the FR-9 performance fix (`ScheduleInstance` DTO, not `Transaction::replicate()`) by asserting the query count doesn't grow with occurrence count — the same technique the 3 proposed N+1 tests below should reuse.

## Proposed tests

### Finding 1 — DoS via unbounded-cost recurrence (`BudgetRequest`/`TransactionRequest`)

- **`test_budget_start_date_before_a_sane_floor_is_rejected`** (`BudgetApiTest` or new `BudgetRequestTest`) — `POST /api/v1/budgets` with `start_date: '1000-01-01'`, `frequency: 'DAILY'` → assert 422 once a minimum-date rule (e.g. `after_or_equal:1900-01-01`, matching whatever floor the fix picks) is added to `BudgetRequest::rules()`. Negative case: `start_date` at or after the floor still passes validation (existing tests already cover this implicitly).
- **`test_schedule_config_start_date_before_a_sane_floor_is_rejected`** — same shape against `TransactionRequest`'s `schedule_config.start_date`/`original_schedule_config.start_date` (`TransactionRequest.php:165-172,211-221`).
- **`test_recurrence_rule_service_bounded_calls_stay_within_a_time_budget_for_an_ancient_daily_start_date`** (`RecurrenceRuleServiceTest`, **guarded-live** — wall-clock assertions are inherently a bit flaky on shared CI runners) — `hasOccurrenceOnOrAfter()`/`getOccurrencesAfter()` with `start_date = now()->subYears(1000)`, `frequency = DAILY` must complete under a generous fixed budget (e.g. 500ms), documenting the ceiling this fix is meant to hold even for legacy rows that predate the new validation floor.
- Type: integration (validation) + unit (service, guarded-live for the timing assertion).

### Finding 2 — `BudgetPolicy::create()` no-op / FormRequest as sole gate

Not independently unit-testable at the Policy layer (there's nothing there to test) — the meaningful regression guard is a **coupling test** that fails loudly if the FormRequest checks it currently relies on are ever weakened:

- **`test_ownership_validation_rules_are_present_on_every_budget_request_field_that_references_another_table`** (new `BudgetRequestTest`, unit, reflection-based) — assert `BudgetRequest::rules()['category_id']` and `['account_id']` each contain a `Rule::exists` (or equivalent closure) scoped by `user_id`. This makes "the ownership gate was silently removed from the only layer that has one" fail a test instead of only a docs note.
- The existing `test_user_cannot_use_another_users_category`/`test_user_cannot_use_a_payee_as_the_account` (`BudgetApiTest.php:111-151`) already cover the *behavioral* half of this from the outside — the gap is only that nothing pins the *mechanism* (Policy vs. FormRequest) so a refactor that moves the check without preserving it would still show existing tests green until data actually leaks.
- Type: unit.

### Finding 3 — N+1 in `TransactionApiController::getScheduledItems()`

- **`test_get_scheduled_items_with_budgets_does_not_issue_a_query_per_budget_row`** (new, `tests/Feature/API/TransactionApiControllerTest.php` or a dedicated file) — create 3+ `Budget` rows (mix of account-scoped and account-agnostic) for one user, call `GET /api/v1/transactions/scheduled-items?includeBudgets=1`, `DB::enableQueryLog()` around the call, assert the query count doesn't grow when going from 1 budget to N budgets (same differential technique as `TransactionScheduleInstancesTest.php:62-90`). Negative case: without the eager-load fix, this test fails by showing query count scaling linearly with row count.
- Type: integration.

### Finding 4 — N+1 in `ReportApiController::budgetChart()`

- **`test_budget_chart_with_many_account_agnostic_budgets_does_not_issue_a_query_per_budget_row`** (new, alongside `ReportApiBudgetChartTest.php`) — create several account-agnostic `Budget` rows for distinct categories, call `GET /api/v1/reports/budget-chart`, assert query count is flat as row count grows (same technique as Finding 3's proposed test). Should also assert the *value* returned still matches `$baseCurrency` for the account-agnostic rows, so the eventual fix (reusing `$baseCurrency` instead of recomputing) doesn't silently change behavior.
- Type: integration.

### Finding 5 — unchunked whole-table load in `CalculateTransactionScheduleActiveFlags`

- **`test_command_chunks_rather_than_loading_the_whole_table`** (extends `CalculateTransactionScheduleActiveFlagsCommandTest.php`) — with the fix applied (`chunk()`/`lazy()` or a `cursor()`), assert the command still dispatches exactly one job per schedule/budget row across multiple chunk boundaries (e.g. seed `> chunk size` rows) — a correctness check on the refactor, not a memory-usage assertion (memory ceilings aren't reliably assertable in PHPUnit). Negative case: no row is skipped or double-dispatched at a chunk boundary.
- Type: integration.

## Recommended CI gate

The project already runs `vendor/bin/sail artisan test --compact`; this feature's existing suite (`BudgetTest`, `BudgetServiceTest`, `InflationCalculatorTest`, `RecurrenceRuleServiceTest`, `TransactionScheduleTest` Unit+Feature, `TransactionScheduleInstancesTest`, `TransactionScheduleInstancesInflationTest`, `BudgetApiTest`, `ReportApiBudgetChartTest`, `CalculateTransactionScheduleActiveFlagsCommandTest`) is all `RefreshDatabase`/`DatabaseMigrations` + `Sanctum::actingAs`, no external services — it already belongs in, and runs in, the standard suite. All 4 non-timing proposed tests above (Findings 2-5, plus both validation-layer tests for Finding 1) are the same shape and should land in the same suite. Only the wall-clock assertion in Finding 1's `RecurrenceRuleService` timing test should be marked `guarded-live` / excluded from a hard-fail default run, since a shared CI runner's clock is not a reliable budget-hit signal — a stricter alternative is to skip the timing assertion entirely once the validation floor (the other two Finding-1 tests) makes the pathological input unreachable in practice, and keep only those.

```yaml
# .github/workflows/tests.yml (illustrative — adapt to the repo's actual CI file/runner)
- name: Run test suite
  run: vendor/bin/sail artisan test --compact
```

Branch protection: require this check before merging `feat/budget_redesign` into `develop`. `BudgetMigrationTest` uses `DatabaseMigrations` (real rollback/re-migrate, not just transaction rollback) because it exercises DDL directly — confirm the CI runner's test DB user has the privileges that requires (same as any other migration-touching test in this repo already).

## Gaps — documented but unverified

Ranked by what crossing them exposes:

1. **[HIGH] Finding 1 — DoS via unbounded-cost recurrence has no validation-layer floor and no regression test.** This is reachable synchronously and unauthenticated-adjacent (any verified user, no special privilege) from `POST/PATCH /api/v1/budgets` and the transaction catch-up-schedule flow — the highest-severity item in this whole map because it's a request-latency/availability issue triggerable by a single crafted request, not just a data-correctness bug. Fix (validation floor) is cheap; see proposed tests above.
2. **`catchUpToDate()`'s 10,000-iteration cap is undemonstrated by any test.** Every existing catch-up test uses a schedule that resolves in well under 10,000 iterations, so the cap-hit path (`RuntimeException` at the controller layer, `false` return with no partial `save()` at the model layer) has never actually executed under test. Directly adjacent to Finding 1 — the same ancient-`start_date` input that makes each `RecurrenceRuleService` call slow is also what would drive `catchUpToDate()` toward the cap.
3. **`BudgetPolicy::create()` returning `true` unconditionally means the Policy layer has zero test surface for budget creation ownership** — the entire guarantee rests on `BudgetRequest`'s `Rule::exists()` calls, which *are* tested, but nothing pins that this is the only layer, so a future refactor could silently drop the check without any existing test failing until real cross-user data leaks. Proposed reflection-based coupling test above closes this cheaply.
4. **Two independent, un-tested N+1s (Findings 3 and 4) share the same root cause** (`Budget::currency()` called per-row instead of eager-loaded/reused) in two different controllers — worth fixing together since the fix pattern is identical, even though the call sites are unrelated in the code.
5. **`Transaction::scheduleInstances()` silently ignoring `by_day`/`by_month`** is flagged as a genuine, named drift from FR-5's intent in `architecture.md` itself, but no test demonstrates the actual wrong output (e.g. an ordinal-weekday schedule's forecast series landing on the wrong dates) — only the *correct* behavior of the sibling code paths (`TransactionSchedule::occursOn()`/`getNextInstance()`, `RecurrenceRuleService`) is pinned. A test that shows `scheduleInstances()` diverging from `getNextInstance()` for the same ordinal-weekday schedule would make this drift concrete instead of only documented.
6. **`ApiAbilityEnforcementTest`'s data provider only covers `budgets.index`/`budgets.store`**, not `getItem`/`update`/`destroy` — the Policy-level ownership check on those 3 actions *is* tested (`BudgetApiTest`'s 403-not-404 case), but whether the `abilities:read`/`abilities:write` Sanctum gate specifically blocks a same-owner request that merely lacks the right token ability is unverified for those 3 actions. Cheapest fix: add the 3 missing rows to the existing data provider, following `permissions.md`'s own documented mapping — no new test file needed.
7. **`CalculateBudgetActiveFlag`'s daily-job code path exists only as the second (integration, end-to-end) test in `CalculateTransactionScheduleActiveFlagsCommandTest`** — there's no dedicated unit test for `CalculateBudgetActiveFlag::handle()` in isolation (e.g. asserting `saveQuietly()` doesn't re-fire the `updating` hook / dispatch `CalculateAccountMonthlySummary`, per `architecture.md`'s explicit callout that this is intentionally different from the synchronous create/update path). Low priority — the integration test already proves the externally-observable outcome.
