# Architecture: Budget/Schedule Redesign

## Overview

This feature replaces a single overloaded `Transaction.budget` boolean with two cleanly separated concepts:

1. **A scheduled standard withdrawal/deposit transaction's categorized items now always count toward category budget-vs-actual comparison** — no flag, no opt-out. `schedule` remains the only planning-mode boolean on `Transaction`.
2. **A new standalone `Budget` entity** (`app/Models/Budget.php`, table `budgets`) — a category-level spending/income target with no linked transaction, for the case where no real transaction backs the target at all (e.g. "about this much on groceries" with no fixed payee/date/account).

The two are siblings, not variants: a schedule is "a real, specific event I expect"; a `Budget` is "a target level for a category with no concrete transaction to schedule." Both feed the same category budget-vs-actual chart and (when account-scoped or schedule-derived) the same account-balance forecast bucket, but through structurally separate code paths that are summed, never reconciled.

Full rationale lives in the pre-existing specification set (`.ai/docs/specifications/budget-schedule-redesign/`); this document and its siblings describe the implemented result, cross-referencing where the two diverge.

## What Changed vs. the Old Model

- **Removed**: `transactions.budget` column, `Transaction::byScheduleType()` scope (all variants: `budget`, `budget_only`, `both`, `any`, `schedule_only`), the budget checkbox/section in `TransactionFormStandard.vue`, `app/Console/Commands/CheckBudgetMigration.php` (a temporary 3.x pre-migration audit command, deleted now that the one-time transforming migration has run — see Migration below).
- **Added**: `Budget` model + `budgets` table, `BudgetService`, `BudgetApiController`, `BudgetPolicy`, `BudgetRequest`, `RecurrenceRuleService` (extracted shared period-math), `InflationCalculator` (extracted shared compounding math), `ScheduleInstance` (`app/Support/ScheduleInstance.php`, a non-Eloquent DTO replacing `Transaction::replicate()` for virtual forecast occurrences), ordinal-weekday recurrence (`by_day`/`by_month`, e.g. "first Wednesday of every month") and, later, two month-end patterns (`days_before_month_end`, `last_business_day_of_month`) on both `transaction_schedules` and `budgets` — stored as a single `rrule` column rather than one column per field, see the `HasRecurrenceRule` bullet below.
- **Changed**: `Transaction::isSchedule()` scope replaces `byScheduleType()`; `ReportApiController::budgetChart()` now sums schedule-derived items *and* all active `Budget` rows per category; `CalculateAccountMonthlySummary::getAccountBalanceBudgetData()` reads only `Budget` rows (attributed per `account_id`, or the account-agnostic bucket when null); `transaction_details_standard.account_from_id`/`account_to_id` are now `NOT NULL` (previously nullable only to support budget-only fake transactions).

### Migration from the old model

The old model stored a standalone budget target as a fake `Transaction` (`schedule=false, budget=true`, no real account required). The transforming migration (`database/migrations/2026_08_05_000002_transform_budget_transactions_to_budgets.php`) converts every such row — plus the narrow `schedule=true, budget=true` hybrid with no account on either side — into one `Budget` row per distinct category among its items, then **hard-deletes** the source transaction and its config. It refuses to run (throws, no DDL yet issued) if any of four risk cases are present: zero-item budget transactions, payee-attributed (not account-attributed) budget transactions, stray transfer/investment rows with `budget=true`, or a currency mismatch between the fake transaction and its linked account — mirroring the retired `app:check:budget-migration` command that shipped separately in a prior 3.x release for self-hosted operators to self-audit ahead of time (per `specification.md` §7.1/§12). `down()` for this migration is intentionally a no-op — see the migration's own docblock and `specification.md` §7.3. The following migration (`..._000003_drop_budget_column_and_enforce_account_not_null.php`) then drops `transactions.budget` and tightens `transaction_details_standard`'s account columns to `NOT NULL`, itself re-verifying zero remaining null-account rows before issuing DDL.

## Tech Stack Notes Specific to This Feature

- **`recurr/recurr`** (pre-existing dependency, now used more heavily) — both `TransactionSchedule` and `Budget` express their recurrence as a `Recurr\Rule` evaluated through `Recurr\Transformer\ArrayTransformer`. As of the RRULE storage addendum (see below), the rule's frequency/interval/start/end/count/`by_day`+`by_month`/month-end-pattern components are never passed around as separate parameters — they're composed into a single RFC 5545 RRULE string once, by the owning model.
- **`RecurrenceRuleService`** (`app/Services/RecurrenceRuleService.php`) — the shared calendar-occurrence engine extracted from `TransactionSchedule`'s previously-inline `getRecurrence()`. Every public method (`getRecurrence()`, `getOccurrencesAfter()`/`hasOccurrenceOnOrAfter()`, `getRecurrenceBetween()`, `occursOn()`, and the `buildRule()` core) takes a single `(Carbon $startDate, string $rrule, ...)` shape — `buildRule(Carbon $startDate, string $rrule): Rule` is simply `Rule::createFromString($rrule, ...)`, and is the **only** runtime place a `Recurr\Rule` gets constructed from a start date and RRULE string for occurrence evaluation (`HasRecurrenceRule::effectiveRrule()` builds a `Rule` too, but only to serialize discrete fields into the stored string, and the `transaction_schedules` RRULE backfill migration carries its own private, throwaway assembler for the legacy columns; neither evaluates occurrences) (`public`, since `Transaction::scheduleInstances()` calls it directly to run its own `ArrayTransformer`/constraint with a caller-supplied `virtualLimit`). Composing that RRULE string from discrete fields is no longer this service's job at all — see `HasRecurrenceRule` below. `estimatePeriodsBetween()` is the one exception to the single-rrule-parameter shape's *callers*: `ValidatesRecurrenceRule::maxRecurrencePeriodsRule()` still validates raw `frequency`/`interval` request fields (the request contract didn't change), so it builds a minimal `"FREQ=...;INTERVAL=..."` fragment just to feed this method. Its own `RECURRENCE_VIRTUAL_LIMIT` is raised to 100,000 (from Recurr's default 732) specifically to avoid silently truncating long-lived DAILY rules.
- **`HasRecurrenceRule`** (`app/Models/Concerns/HasRecurrenceRule.php`, per the RRULE storage addendum — see `.ai/docs/specifications/budget-schedule-redesign/recurrence-rrule-storage.md`) — shared by `TransactionSchedule` and `Budget`. Both tables store recurrence as one `rrule` (RFC 5545 RRULE string) column instead of one column per component (`frequency`/`interval`/`count`/`end_date`/`by_day`/`by_month`, plus the two month-end patterns below); this trait exposes those as virtual `Attribute::make()`-backed properties (`count` is the one exception — see below) that decompose out of `rrule` on read and record a pending value on write, composed back into `rrule` once per `fill()`/`save()` call (`composeRrule()`), not per-field. `effectiveRrule()` recomputes the RRULE live from current field state (pending-or-decomposed) rather than only reading the persisted column, so an unsaved model (e.g. `TransactionRequest::nextDateOccursOnRule()`'s validation-only `new TransactionSchedule([...])`) still resolves correctly. `count` is backed by `App\Casts\RecurrenceCountCast` (a real `casts()` entry) instead of the trait's usual same-named-method convention: Eloquent's `Model::__callStatic()` implements every undefined static call, including the aggregate `Budget::count()`/`TransactionSchedule::count()`, as `(new static)->$method(...)` — a real instance method literally named `count()` would silently intercept that call instead of forwarding to the query builder. The two month-end patterns (`days_before_month_end`, 0-27; `last_business_day_of_month`, boolean) are request-only/virtual with **no backing column at all** — `days_before_month_end` composes to a single negative `BYMONTHDAY`, `last_business_day_of_month` composes to `BYDAY=MO,TU,WE,TH,FR;BYSETPOS=-1`, both mutually exclusive with `by_day` (validated in `ValidatesRecurrenceRule`).
- **`InflationCalculator`** (`app/Services/InflationCalculator.php`) — a small, standalone compounding utility (`applyAnnualRate()`), deliberately *not* part of `RecurrenceRuleService`: the recurrence service decides which periods exist, this decides what multiplier applies to a given period's amount. Compounds once per calendar-year boundary (not on `start_date`'s anniversary). Consumed by `Transaction::scheduleInstances()`, `ReportApiController::budgetChart()`, and `CalculateAccountMonthlySummary::getAccountBalanceBudgetData()`.
- **`ScheduleInstance`** (`app/Support/ScheduleInstance.php`) — a plain, non-Eloquent attribute/relation bag replacing `Transaction::replicate()` for virtual (never-persisted) forecast occurrences, fixing the per-occurrence Eloquent-clone overhead documented in `forecast-performance.md` (FR-9). Behaves like a mutable magic-property bag so existing call sites that stash ad-hoc computed fields onto a "transaction" keep working unchanged.
- **`CalculateBudgetActiveFlag`** (`app/Jobs/CalculateBudgetActiveFlag.php`) — a queued job recomputing one `Budget`'s `active` flag (`saveQuietly()`, no model events re-fired). Dispatched per-row from `app:cache:transaction-schedule-active-flags` (`app/Console/Commands/CalculateTransactionScheduleActiveFlags.php`), which pages through both the schedule and budget tables via Eloquent's `lazy()` (bounded-chunk cursor, not `get()`/`all()`) rather than loading every user's rows into memory at once, and which also still dispatches the pre-existing `CalculateTransactionScheduleActiveFlag` per real schedule. Both run daily via `routes/console.php` (`->dailyAt('00:00')`).
- **Budget/schedule recurrence cost is bounded at validation time.** `ValidatesRecurrenceRule::maxRecurrencePeriodsRule()` (`app/Http/Traits/ValidatesRecurrenceRule.php`), shared by `BudgetRequest` and `TransactionRequest`, rejects a `start_date`/`frequency`/`interval` combination that would span more than 2000 periods (e.g. a DAILY rule with a `start_date` a decade in the past) — every later `RecurrenceRuleService` call on such a rule (`isActive()`, `getNextInstance()`, catch-up) would otherwise resolve an occurrence relative to "today" by scanning that many candidates, which is measurably slow (reproduced at ~4s/call for a centuries-old start date). This is a request-latency/availability guard, not just a UX nicety: it runs synchronously on every `Budget`/schedule create or update.
- **Currency resolution avoids a per-row query in both `Budget`-listing read paths.** `Budget::currency()` lazy-loads `account->config->currency` (for an account-scoped budget) or falls back to `user->baseCurrency()` (for an account-agnostic one) — the latter re-queries regardless of eager-loading, since it builds a fresh relation query rather than reading a loaded collection. `TransactionApiController::getScheduledItems()` and `ReportApiController::budgetChart()` both eager-load `account.config.currency` and call `->currency()` only for account-scoped rows (`$budget->account_id ? $budget->currency() : $baseCurrency`), reusing one pre-computed `$baseCurrency` for every account-agnostic row instead. Preserve this pattern when touching either method — reverting to an unconditional `$budget->currency()` per row reintroduces an N+1 that scales with the number of account-agnostic budgets returned.

## Trust Boundaries

| Boundary | Enforcement |
|---|---|
| Browser → `GET/POST/PATCH/DELETE /api/v1/budgets*` | `auth:sanctum` + `verified` + `abilities:read` (`index`, `getItem`) / `abilities:write` (`store`, `update`, `destroy`) — declared as class-level `#[Middleware(...)]` attributes (`app/Http/Controllers/API/BudgetApiController.php:16-23`; the codebase-wide move from the older `HasMiddleware`/static-`middleware()` pattern to PHP 8 attributes landed as part of the Laravel 13 upgrade, see `.ai/docs/features/api-access-and-2fa/permissions.md`'s "Mechanism" section), matching the project-wide ability-enforcement pattern. |
| Who can create/view/edit/delete a `Budget` | **Owner-only, no shared/household access.** `BudgetPolicy::isOwnItem()` (`app/Policies/BudgetPolicy.php:16-19`) is a straight `$user->id === $budget->user_id` check, backing `view`/`update`/`delete`/`restore`/`forceDelete`. `viewAny`/`create` both return `true` unconditionally (any authenticated user may list their own or attempt to create) — the real ownership gate for `create` is not in the Policy at all; see `permissions.md` for exactly where it lives. |
| `category_id`/`account_id` cross-user reference | Enforced in `BudgetRequest::rules()` (`app/Http/Requests/BudgetRequest.php:33-40`), not the Policy or the model — both use `Rule::exists(...)->where('user_id', $this->user()->id)` (the account rule additionally requires `config_type = 'account'`, rejecting a payee id). A user cannot attach a `Budget` to another user's category/account, nor to a payee. |
| `Budget.user_id` | Auto-filled from the resolved `$user->budgets()->create()` relation in `BudgetService::store()`, and defensively from `ModelOwnedByUserTrait`'s `creating` hook (`app/Http/Traits/ModelOwnedByUserTrait.php:24-28`) if not already set — `user_id` is **not** in `Budget::$fillable`, so it can never be set from client-supplied request data directly. |
| `Budget.active` | Never client-settable — not in `$fillable`, always recomputed server-side via `Budget::booted()`'s `creating`/`updating` hooks (`app/Models/Budget.php:103-112`) and the daily recalculation job. |
| Recurrence-rule shape (`frequency`/`interval`/`start_date`/`end_date`/`count`/`by_day`/`by_month`/`days_before_month_end`/`last_business_day_of_month`) | Validated in `BudgetRequest` using the same `ValidatesRecurrenceRule` trait (`app/Http/Traits/ValidatesRecurrenceRule.php`) `TransactionRequest`'s schedule config already used — shared, not reimplemented. The three month-scoped patterns are mutually exclusive (`prohibitedIf`), require MONTHLY/YEARLY, and a YEARLY pattern requires `by_month`. |
| The persisted `rrule` string | **Never client-supplied.** Not in `$fillable`, `#[Hidden]` from serialization; composed server-side by `HasRecurrenceRule::composeRrule()` from the validated discrete fields (`frequency` is `Rule::in`, `by_day` is regex-anchored, the rest are bounded integers/booleans), so the stored string is only ever built from validated components. |
| `ReportApiController::budgetChart()` / `TransactionApiController::getScheduledItems()` reading `Budget` rows | Both scope every query to `->where('user_id', $request->user()->id)` inline — there is no per-row `Gate::authorize()` call in either read path, since these are already user-scoped aggregate/list endpoints (same pattern as the rest of `ReportApiController`). `ReportApiController` and `TransactionApiController` are both gated by the project-wide `abilities:read` middleware. |

## Known Risks / Assumptions

- **The RRULE-storage migrations were edited in place on the unreleased `release/v4` line.** `2026_08_05_000001_create_budgets_table` was rewritten (no `frequency`/`interval`/… columns, `rrule NOT NULL`), the `2026_08_04_000001_add_by_day_to_transaction_schedules_table` migration was deleted and replaced by a 3-step `rrule` sequence (`add` → `backfill` → `drop`, guard-before-DDL), and `2026_08_29_000002`'s `down()` was rewritten. Laravel tracks migrations by filename, so a database that already ran the earlier pre-release content keeps the old `budgets` columns while the code expects `rrule`; such a pre-release database must be recreated (no repair path ships). The real 3.x → 4.0 path (never had `budgets`, has legacy `frequency`/`interval`/`count`/`end_date` on `transaction_schedules`) is covered by the backfill/drop sequence and `TransactionScheduleRruleMigrationTest`. Both conversions are irreversible once the old columns drop.
- **The RRULE-building logic exists in three hand-synced copies.** PHP `HasRecurrenceRule::effectiveRrule()`, JS `processScheduledTransaction()` (`resources/js/shared/lib/helpers/index.js`), and the form preview in `TransactionSchedule.vue` each independently translate the discrete pattern fields into RRULE components. There is no JS test runner in the repo, so nothing catches drift between them.

- **`Budget.active` computed synchronously on every create/update, not just via the daily job.** `Budget::booted()` (`app/Models/Budget.php:103-112`) calls `RecurrenceRuleService::hasOccurrenceOnOrAfter()` inline on every save — bounded/cheap by design (see the method's own docblock, `RecurrenceRuleService.php:124-134`), but it does mean a slow or malformed rule affects request latency for `store`/`update`, not just the background job.
- **No shared/household access model exists for `Budget`** (or for any other domain entity in this codebase) — ownership is strictly single-user (`user_id` FK), matching the project's existing single-tenant-per-user design (see `.ai/docs/product-context.md`). Not a gap introduced by this feature, just worth stating since a security audit will otherwise ask.
- **The budget-vs-actual chart's per-category total is an intentionally un-deduplicated sum.** An account-scoped `Budget` row and an account-agnostic row for the same category both count (`ReportApiController::budgetChart()`, `app/Http/Controllers/API/ReportApiController.php:244-258`) — by design, per `background.md` "Account Scoping for Budgets," not a bug. The only safeguard is the FR-7 breakdown/drill-down exposing which rows contributed.
- **The migration's irreversibility is real and undocumented risk if run without a backup.** `2026_08_05_000002_transform_budget_transactions_to_budgets.php::down()` is a no-op; the only recovery path after a bad conversion is a database restore. `UPGRADE.md`'s "Upgrade from YAFFA 3.x to 4.x" section is the documented mitigation (mandatory backup step) — verify it exists and is current if auditing release readiness.
